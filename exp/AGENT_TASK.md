# Задание: датасет для проверки disambiguation + сравнительные тесты exp3a/4a/exp5

## Контекст

Три версии памяти в репозитории qwen-memory-adapter:
- `exp3a_vector_injection.py` — базовая (точечный ключ, статический гейт)
- `exp4a_windowed_key.py` — + ключ из локального окна вокруг удивившего токена
- `exp5_ctx_dynamic_gate.py` — + динамический гейт (энтропия Qwen × уверенность
  роутинга памяти) + честная кросс-сессионная проверка через диск

На текущем `dataset_yattn.pt` разница между версиями почти не видна, потому что
в каждом примере — ОДИН секрет каждого типа. Проблема, которую эти версии должны
чинить (интерференция «пароль/пин-код» на масштабе, отмечена в `docs/RESULTS.md`
и результатах `exp2n_full`), проявляется только когда в одном контексте
**несколько секретов одного типа**, различающихся объектом-referent'ом.

## Шаг 1 — сгенерировать multi-type датасет

Взять `gen_yattn.py` как основу (тот же пайплайн: прогон через Qwen, сбор
`ctx_hidden`, `q_hidden`, `h_inA_all`, `h_outB`, `entropy`), но изменить шаблон
промптов так, чтобы в одном контексте было 2–4 секрета **одного типа**, у каждого
явный referent-токен рядом:

```
Пароль от почты: X8k2. Код доставки: 4471. Пароль от телефона: Q91z.
Пин-код банковской карты: 8834. Пароль от ноутбука: Z014.
```

Вопрос указывает referent явно:
```
Какой пароль от телефона?
```

Требования к датасету:
- **минимум 2 referent'а на тип** (пароль/почта vs пароль/телефон vs пароль/ноутбук
  и т.д.) в каждом примере — иначе коллизии негде проявиться;
- referent-слово должно стоять **и до, и после** секрета примерно поровну по
  датасету (не всегда «пароль от X: значение» — иначе модель выучит фиксированную
  позицию, а не реальный семантический якорь);
- сохранить поле `type` как раньше, но добавить новое поле `referent` (то, к чему
  привязан секрет — «почта»/«телефон»/«ноутбук» и т.д.) — нужно для метрики
  confusion ниже;
- 300–400 примеров минимум (как в исходном `gen_yattn.py`), с MAX_CTX_S<200 как
  в текущих скриптах, чтобы совместимо с `N_TRAIN=64` и текущими гиперпараметрами;
- сохранить в `dataset_multitype.pt` тем же форматом (список dict), не ломая
  совместимость с существующими `write_work`/`mix_vec`.

Если формат `gen_yattn.py` (тегирование `entropy`, порядок полей) не совпадёт с
тем, что я предполагаю по коду `exp2n`/`exp3a` — подогнать поля под реальный
`gen_yattn.py`, а не под это описание.

## Шаг 2 — новая метрика: confusion между референтами одного типа

В `eval`-циклах (в in-process val и в `cross_session_eval`) добавить, помимо
`acc6`/`acc_open`/`per_type`:

```python
confusion = {}  # (true_referent, predicted_referent) -> count
```

Predicted referent определяется по тому, какой секрет (какого referent'а) реально
выдала модель (сравнить сгенерированный top-1 токен/vector со значениями всех
секретов данного типа в этом примере, не только с правильным). Итоговая таблица:
сколько раз модель перепутала «пароль от почты» с «пароль от телефона» и т.п.

## Шаг 3 — прогнать все три версии на обоих датасетах

Всего 6 запусков:

| Скрипт | dataset_yattn.pt (текущий) | dataset_multitype.pt (новый) |
|---|---|---|
| exp3a_vector_injection.py | запустить, зафиксировать acc6/acc_open | запустить, + confusion |
| exp4a_windowed_key.py | запустить | запустить, + confusion |
| exp5_ctx_dynamic_gate.py | запустить (включает cross_session_eval) | запустить, + confusion |

Для каждого запуска сохранить лог целиком (stdout) в `logs/<script>_<dataset>.log`.

## Шаг 4 — итоговая сводная таблица

Собрать в `RESULTS_exp4_exp5.md`:

```
| Схема | dataset | acc6 | acc_open | confusion (в среднем на пример) | cross-session acc_open |
```

Гипотезы, которые эта таблица должна подтвердить/опровергнуть:
1. На `dataset_yattn.pt` разница между exp3a/4a/exp5 небольшая (мало где коллизии).
2. На `dataset_multitype.pt` exp4a/exp5 заметно снижают confusion относительно exp3a.
3. exp5 (динамический гейт) не хуже exp4a по acc_open на dataset_yattn.pt
   (гейт не должен портить то, что и так работало) и не хуже на multitype.
4. `cross_session_eval` в exp5 (через диск) даёт **тот же** acc_open, что и
   in-process val в той же эпохе — если разница есть, значит где-то теряются
   данные при сериализации `work` (важно проверить отдельно, это баг, а не
   особенность схемы).

## Шаг 5 — sanity-check реальной межпроцессной персистентности

Отдельно, вручную, на паре примеров:

```bash
python session_write.py --ckpt exp5_ctx_gate.pt --example_idx 5 --out /tmp/mem5.pt
# процесс завершился, переменные питона уничтожены
python session_read.py --ckpt exp5_ctx_gate.pt --example_idx 5 --mem /tmp/mem5.pt
```//
Проверить `match=True` в выводе `session_read.py`. Это подтверждает, что схема
реально работает между independent процессами ОС, а не только внутри одного
питон-процесса с общим RAM.

## Что НЕ делать на этом шаге

- не трогать 4b/4c/4d/4e (raw-attention key, per-type routing heads,
  explicit type-token, DCT) — это следующая итерация, после того как станет
  ясно, дал ли windowed key + dynamic gate эффект вообще;
- не менять N_SLOTS/CHUNK/ETA/GAMMA — держать гиперпараметры фиксированными
  между всеми 6 запусками, иначе сравнение станет нечестным.
