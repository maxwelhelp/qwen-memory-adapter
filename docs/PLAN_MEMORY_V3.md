## Методологические правила (сквозные)

1. **Одна переменная на эксперимент** — иначе не поймём, что повлияло.
2. Числа — только с размером выборки; выводы — детерминированной проверкой (greedy, seed), не сэмплингом.
3. Каждый завершённый шаг: **коммит + пуш сразу**.
4. Отчёты — в `docs/REPORT_WORK.md`, дополняется после каждого шага.
5. Архитектурные решения — только пользователь (гейты ниже). Агент готовит данные и варианты.
6. Эксперимент меняет ровно одну вещь; сравнение — на ОДНОМ И ТОМ ЖЕ датасете/протоколе.

## Фаза 1 — Проверка обучаемости памяти: батарея архитектурных вариантов (переформулирована 2026-08-04 по указанию пользователя)

идти по плану, пока не проверим на разных вариантах архитектур — учится ли память или нет
и даёт ли пользу». Текущая схема (сдвиг логпробов 6 кандидатов) = голосование за закрытый
список, считается НЕ победой. Alignment (M(h)≈h) сделан — пространства общие; вопрос —
обучаемость и польза памяти как таковой.

**Статус фактов:** alignment работает (smoke Ф0: val 1.33→0.21);
‖Δ_in‖ ≈ 36 (норма вектора; генератор печатает mean квадрата КОМПОНЕНТА = 1.465,
отсюда ошибочная оценка «1.2» в ранних записях — исправлено 2026-08-04);
запись в v5 — необучаемая механика с detach-клонами (обход bilevel-провала 7 прогонов);
ORACLE-тест (2026-08-04): идеальная инъекция (сам target_in, норма ~36) во вход последнего
слоя даёт acc6 = 1.00 — последний слой ПРОПУСКАЕТ и усиливает возмущение входа
(‖Δ_out‖ ~276, усиление ~7.7×). Направление векторной инъекции жизнеспособно —
проблема была в обучении МАСШТАБА mix (см. отчёт exp1b).

**Варианты (по одному прогону каждый, общий датасет, общие метрики):**
- **A. Контроль — текущая схема (логпроб-сдвиг 6 чисел):** baseline-точка в той же таблице
  (известно: линейные 34/40, MLP+η 24/40).
- **B. Векторная инъекция во вход последнего слоя** (`exp1b_input_injection.py`):
  `W_out: 896→896`, `h_in[-1] += g·W_out(read_diff(q, work))`, полный forward последнего
  слоя С инъекцией, `loss = MSE(h_out', h_outB) + 0.5·CE`. Метрики: val_mse,
  acc по 6 кандидатам, **acc по ОТКРЫТОМУ словарю** (argmax всего lm_head == секрет),
  norm(mix − target_in) (точность инъекции), per-type. Запись — механика как v5.
- **C. Bilevel TTT-стиля, минимальный тест** (`exp1c_bilevel_smoke.py`): 1 слот,
  запись АРИФМЕТИКОЙ без detach (θ ← θ(1−γ) − η·∇, граф через ВСЕ шаги,
  `create_graph=True`), обучаемые η/γ, пары (k→v) на синтетике.
  Режимы: bilevel (граф через шаги) vs detach (как v5) — сравнить: доходит ли градиент
  до η/θ₀, улучшает ли оптимизация чтение пар. Прямой ответ «учится ли запись».

**Гейт (решение пользователя по результатам A/B/C):**
- B достижим (acc_open значимо > шанса, MSE сходится) → векторная память (открытый словарь)
  становится основным направлением;
- C показывает обучаемость записи → полный bilevel («память учится всегда») — главный путь;
- ни B, ни C не работают → дизайн пересматривается (честно, без упрощений: «что-то не то
  делаем» — разбор причин + новые варианты).

## Фаза 7 — «Слоты — это уже MoE?» — настоящий sparse MoE (вариант пользователя, 2026-08-04)

**Разбор пользователя (вставлен в план дословно по смыслу):** структурно да — N=32
независимых «экспертов» (слотов) + маршрутизация (`w = softmax(q · W_route)`) — это
MoE-паттерн (gating + эксперты). Но это не классический MoE, а собранный вручную гибрид
с асимметрией:

- запись маршрутизируется через `argmax(h · route_keys)` — НЕ обучается, ключи случайные;
- чтение маршрутизируется через `softmax(q · W_route)` — обучается дистилляцией;
- активны на чтении все 32 слота (softmax-взвешенная сумма), не top-k — dense-MoE,
  не sparse-MoE.

**Гипотеза:** случайная маршрутизация записи — вероятная причина слабости типа «Код»
(4/10 в прошлом межсессионном тесте, RESULTS.md) — секреты типа могут ложиться в один
слот случайно и интерферировать.

**Что дочитать/доисследовать:**
- `RESULTS.md` — разбивка по типам (где именно теряет «Код»);
- `PLAN_MEMORY_V2.md` §7;
- MoE-литература: load-balancing loss (Switch Transformer и аналоги), как в Titans
  устроена маршрутизация записи, приёмы обхода bilevel (главный вопрос — скрестить
  обучаемую маршрутизацию с уже работающей заморозкой записи, §2.4 п.1 мастер-файла:
  маршрут записи обучается дистилляцией как W_route, БЕЗ градиента через шаги записи).

**Эксперименты (по одному под-эксперименту на прогон, потом пакет):**
- **7a — обучаемая маршрутизация записи:** заменить случайные `route_keys` на обучаемый
  маршрут (без возврата bilevel: обучение дистилляцией, градиент не течёт через запись).
  Метрика: per-type accuracy, «Код» — отдельной строкой.
- **7b — top-k чтение + load-balancing loss:** `TOPK=4` вместо dense softmax + LB-лосс
  (иначе маршрутизация схлопнется на несколько слотов). 2b (Ф2) — диагностика top-k БЕЗ
  LB; 7b — с LB, полная картина.
- **7c — полный пакет:** обучаемая запись + top-k + LB вместе; сравнение с рабочим
  dense-гибридом (34/40) на том же датасете и протоколе.

**Критерий успеха:** sparse-MoE ≥ текущего гибрида на той же оценке; per-type — «Код»
не хуже остальных типов.
**Риск:** возврат bilevel-проблемы (градиенты через запись) — отслеживать явно; каждый
под-эксперимент отдельным прогоном; НЕ смешивать с Ф4 (две переменные в одном прогоне).
**Порядок:** после Ф2-Ф3 (top-k чтение уже диагностируется в 2b), старт — только по
явному решению пользователя.
