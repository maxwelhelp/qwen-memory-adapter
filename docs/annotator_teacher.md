# Аннотатор-учитель: модель с будущим вопросом строит датасет важности токенов

Статус: продумано, эксперимент не начат. 2026-08-03.

## 1. Идея

Второй проход модели (аннотатор) получает **контекст + будущий вопрос** и JSON'ом отмечает:
«какие фрагменты текста критически важны для ответа, какие неважны».
Эти метки становятся ДОПОЛНИТЕЛЬНЫМ УЧИТЕЛЕМ для нашего MLP-скоринга важности токенов.

Ключевое отличие от прошлой постановки: датасет строится ОФЛАЙН → вопрос известен →
аннотации НЕ слепые (в отличие от эвикции на инференсе, где вопрос приходит позже).

## 2. Почему это сильнее текущих сигналов

| Сигнал | Что видит | Слабость |
|---|---|---|
| attention-масса | текущий запрос (последний токен) | слеп к спящим токенам (dormant) |
| удивление (z-score) | сам токен vs контекст | ловит «неожиданное», но не «нужное» |
| **аннотатор (новый)** | **весь контекст + будущий вопрос** | мнение модели ≠ факт (чинится контрафактикой) |

Аннотатор знает, ЧТО спросят — он может пометить спящий пароль как важный, даже если
внимание на него нулевое. Это ровно то, чего не хватало.

## 3. Схема построения датасета-учителя

```
для каждого примера из датасета:
    ctx   = контекст (префикс)
    q     = будущий вопрос
    ans   = правильный ответ (из датасета)

    промпт аннотатора:
      «Контекст: {ctx}
       Вопрос: {q}
       Верни JSON: {"important": ["фрагмент1", ...], "unimportant": ["фрагмент2", ...]}»

    → маппинг фрагментов на токены (по декодированному тексту, как pw_positions)
    → важность токена: 1 = в important, 0 = в unimportant, нейтральные — пропуск

    (опционально, контрафактическая валидация меток):
      убрать помеченные important  → ответ должен измениться
      убрать помеченные unimportant → ответ не должен измениться
      метки, не прошедшие проверку, отбрасываются
    → target_annot_t для каждого токена
```

## 4. Как встраивается в скоринг (архитектура)

Текущий скоринг: одна сеть, две головы (attn, surp). Добавляем третью:

```
hidden_t ──► backbone ──► голова A: score_attn  (учитель: attention-масса)
                  │      ├─► голова B: score_surp (учитель: удивление z-score)
                  │      └─► голова C: score_annot (учитель: аннотация с вопросом)
                  ▼
         score = score_attn + β·score_surp + γ·score_annot
```

- На инференсе аннотатор НЕ вызывается — скоринг уже выучил «что модель считает
  важным для будущих вопросов».
- γ настраивается на валидации (как β).
- Три головы = мультитаск: общий backbone, каждая голова учится на своём чистом сигнале.

## 5. Связь с критикой-бустом

Это ОФЛАЙН-версия той же идеи (критика → сигналы → приоритеты):
- **Офлайн (этот план)**: аннотатор с вопросом → датасет → третья голова скоринга.
  Дёшево на инференсе (0 дополнительных проходов).
- **Онлайн (позже, опц.)**: аннотатор/критик на инференсе → score += boost·annot
  для конкретного контекста. 2× дорого, но адаптивно.
Порядок: сначала офлайн (учитель), онлайн-буст — только если офлайн дал сигнал.

## 6. Плюсы и риски

Плюсы:
- Метки «что реально нужно для ответа» — принципиально лучше attention-массы;
- Аннотатор видит будущий вопрос → спящие токены помечаются;
- На инференсе — бесплатно (третья голова).

Риски:
- Мнение модели ≠ факт → контрафактическая валидация (раздел 3) обязательна хотя бы
  на подмножестве меток;
- Аннотатор на 0.5B может быть слабым → тест и на 1.5B;
- Маппинг фрагментов → токены грязный (BPE-границы) → перекрытие по символам, как pw_positions;
- JSON может быть невалидным → толерантный парсер (первая JSON-подстрока).

## 7. Дешёвый тест ДО обучения (30 минут)

1. Взять 20 примеров dormant-задачи (пароль в мусоре) + 20 правил-примеров.
2. Аннотатор (0.5B-Instruct) с промптом «контекст + вопрос» → JSON important/unimportant.
3. Посмотреть глазами: помечает ли спящий пароль как important? (да → идея сильна для
   dormant; нет → она полезна только для семантики, решаем, стоит ли).
4. Сравнить метки аннотатора с attention-массой и удивлением: новое ли это знание.
5. Если сигнал есть → генерируем полный датасет аннотаций → третья голова → eval как в
   eval_eviction.py (копия файла под новый эксперимент, как договаривались).

## 8. Вопросы, на которые ответит эксперимент

- Даёт ли аннотатор-учитель прирост сверх attn+surp (γ>0 полезен)?
- Помечает ли аннотатор спящие токены, которые внимание не видит?
- Работает ли контрафактическая валидация (метки = факт, а не мнение)?

## 9. Результаты теста-взгляда (2026-08-03)

Скрипт: `annotator_test.py` (Qwen2.5-0.5B-Instruct, 2-й проход, JSON important/unimportant).

| Задача | Метки | Результат |
|---|---|---|
| Dormant (спящий пароль в мусоре, вопрос «какой пароль?») | пароль в important | **10/10 (100%)** |
| Правила (условие в тексте, вопрос «что делать, если X?») | условие в important | **10/10 (100%)** |

Вывод: аннотатор с БУДУЩИМ ВОПРОСОМ помечает спящие токены (которые attention-масса
не видит никогда) в 100% случаев. Метки точные на уровне фрагментов.

По сути построен ПЕРВЫЙ КУСОК ДАТАСЕТА-УЧИТЕЛЯ, в котором сама сеть (вторым проходом,
с видением будущего вопроса) написала, что в контексте важно, а что неважно.

Осталось (следующие шаги):
1. Полный датасет аннотаций (800+ примеров: dormant + правила + тексты) → маппинг
   фрагментов на токены → target_annot.
2. Третья голова скоринга (attn + surp + annot) → обучение.
3. Eval (копия eval_eviction.py) + контрафактическая валидация меток на подмножестве.
